Vision & Scope Kaizen is a local-first, SOLID-architected system that turns natural-language test steps (e.g., “Open google.com”, “Find the green login button”, “Search for {query}”) into executable browser tests for websites the system has never seen. Deployables: 1. Automation Engine (Program) — runs the tests, interacts with local LLM(s), resolves elements (semantic + optional visual), executes actions via browser automation (Playwright), captures artifacts, learns stable selectors. 2. Automation Portal (Website) — backend + frontend for writing tests, launching runs, reviewing results, and managing models/config. Local-first: Uses open models via Ollama (no cloud/API). Extensible: Add new actions and strategies without touching existing code (OCP). Deterministic & Safe: JSON schema validation, uniqueness/visibility checks, conservative click policy. ⸻ 2) Core Principles • SOLID across all modules (SRP, OCP, LSP, ISP, DIP). • Tool-driven LLM: no phrase hardcoding. LLM selects from a small Action Ontology and returns a JSON plan. • Separation of Concerns: engine ↔ portal boundaries defined by DTOs / OpenAPI; browser automation isolated behind IBrowser. • Security by default: zero secrets in Git, non-root containers, schema validation, guardrails for destructive actions. • Ping-pong iteration: build in small steps; every change must be testable, reviewable, and CI-verified. ⸻ 3) Monorepo Decision (ADR Summary) Decision: Use a monorepo (kaizen/) with clear bounded contexts: engine/, portal/, infra/, docs/. Rationale: Faster iteration across contracts; simpler CI; shared standards. Split Later when: independent release cadence, access controls differ, or external adopters need the engine alone. Preparation: Maintain engine–portal API as versioned OpenAPI/DTOs to allow later repo split with minimal refactor. • ILog: structured logger; DI-provided • IClock: deterministic timing for tests 5.2 Action Ontology (LLM tools) • open(url) • type(target, text, clear?) • click(target) • press(key) • waitFor(target|url|state) • assertVisible(target) • assertText(target, expected, match = equals|contains|regex) • assertUrl(expected, match) • custom(script) (sandboxed) The LLM selects and parameterizes these tools under a JSON schema; engine validates before execution. 5.3 Data Models (DTOs) TestSpec { id, name, steps: StepSpec[], vars, tags } StepSpec { index, text, timeout?, data? } ToolCall { tool, args, meta? } // from LLM TargetQuery { text, hints:{role?, color?, near?}, scope? } Locator { type: "role"|"css"|"xpath"|"id"|"testid", value, framePath?, shadowPath? } LocatorCandidates { primary: Locator, fallbacks: Locator[], confidence, reason, bbox? } PageSnapshot { htmlPath, candidates[], stylesIndexPath, screenshotPath?, frames[] } // candidates: tag/id/class/role/aria/text/visible/clickable/bbox/color Run { id, testId, status, startedAt, finishedAt } StepRun { runId, stepIndex, toolCall, result, reason?, durationMs, evidence } Artifacts { pageScreenshot?, domSnapshot?, consoleLog?, networkLog? } LearnedSelector { domain, path, queryText, locatorProfile, fingerprint, lastSeenAt } 5.4 Element Resolution (ranking signals) 1. Semantic: role=button, accessible name (inner text/aria-label/labelledby), id, data-testid, name, type 2. Heuristics: visible, enabled, size>threshold, region weight (header/nav/main/form/dialog) 3. Proximity: boost nodes near username/password or search fields for auth/search intents 4. ColorStyle: compute final CSS color (cascade/variables). If “green” ambiguous → fallback visual check 5. Visual (optional): VLM on screenshot → region → DOM via elementFromPoint/bbox overlap Verify: uniqueness + interactability; never click hidden/covered/disabled. ⸻ 6) Portal — Responsibilities & API 6.1 Backend (FastAPI recommended—typed, concise) Services (SRP): • ITestService — CRUD test specs, versioning • IRunService — enqueue/monitor runs, cancel • IArtifactService — serve screenshots/DOM/logs securely • IInsightService — learned selectors, trends • IConfigService — model choices, timeouts, privacy policies • IEngineGateway — local process / HTTP / gRPC to engine • IQueue (optional later) — isolate UI from long-running runs Minimal API (MVP): POST /tests -> { testId } GET /tests/{id} -> TestSpec POST /runs -> { runId } GET /runs/{id} -> { status, startedAt, finishedAt } GET /runs/{id}/steps -> [StepRunSummary] GET /runs/{id}/artifacts -> { links } GET /insights/selectors -> { items: [...] } POST /upload/html-snapshot -> { snapshotId } // supports Snapshot Mode GET /config/models -> { textLLMs, visionLLMs, current } POST /config/models -> { ok: true } 6.2 Frontend (React + Vite) • Test Editor: step list, variables, preview JSON plan (LLM dry-run) • Run Dashboard: filterable run list • Run Details: step timeline with before/after screenshots, “why this selector?” explanation, locator/fallbacks • Artifacts Viewer: screenshot with bbox highlight, DOM viewer • Insights: learned selectors per domain, confidence trends • Settings: choose models, timeouts, privacy toggles ⸻ 7) Storage & Artifacts SQLite first (swap to Postgres later through IStorage); artifacts stored on disk: • runs, step_runs, artifacts, page_snapshots, learned_selectors, configs • Paths are recorded in DB. Use Docker secrets / Jenkins credentials. • Containers: non-root user, read-only FS where possible, drop Linux capabilities, pin image digests. • Network policy: LLM runs locally (Ollama); disable outbound calls by default. • Input validation: strict JSON schema for LLM tool plans and API payloads; reject on mismatch and request correction. • Click policy: block destructive actions unless explicitly enabled. • Auth (portal): start local-only; if multi-user, add sessions with HttpOnly, Secure, SameSite=Lax. • CORS: restricted to known origins. • Logging: structured logs; redact tokens; configurable verbosity; avoid storing full page HTML unless needed. • Supply chain: lockfiles, SBOM, image/dependency scans (Trivy/Grype), license allowlist. ⸻ 9) Git Workflow & Commit Hygiene • Trunk-based with short-lived branches (feat/…, fix/…). • Conventional Commits (feat:, fix:, refactor:, docs:, test:, chore:). • Commit reminders: • After scaffolding interface/folder trees • After passing unit tests for a new module • After changing DB schema or OpenAPI • After modifying docker-compose or CI pipelines • After stabilizing a flaky selector (healing added) • Pre-commit hooks: format, lint, typecheck, secrets scan (gitleaks). • CODEOWNERS: engine vs portal owners for focused review. ⸻ 10) Docker & Orchestration 10.1 infra/docker-compose.yml (services) • ollama — local models; volume cache • engine — Playwright browsers preinstalled; depends_on ollama • portal-backend — FastAPI; depends_on engine • portal-frontend — static server (nginx) or dev server • db — SQLite on volume (or Postgres later) • (optional) minio — artifacts at scale Features: healthchecks, mem/CPU limits, non-root users, pinned image digests, named volumes (models/, artifacts/, db/). 10.2 Engine Dockerfile (key points) • Multi-stage build, Playwright browsers installed, non-root UID, copy only needed files, read-only FS where possible. ⸻ 11) CI/CD 11.1 Jenkins (primary) Pipeline stages: 1.
